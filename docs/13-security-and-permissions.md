# 13 — Security & Permissions Specification

**Product:** Offline Restaurant Billing & Management Desktop Application  
**Platform:** Windows desktop, Tauri 2 + React/TypeScript + Rust + SQLite  
**Status:** Implementation specification; configurable decisions are identified below.

## 1. Purpose and boundaries
Protect restaurant operations, financial records, staff accounts, and locally stored data without relying on cloud identity services or internet connectivity. All privileged decisions must be enforced in Rust; hiding a React button is not authorization.

## 2. Threat model
Consider: an unauthorized person using an unlocked POS; a cashier attempting unauthorized discounts/refunds; accidental record modification; theft or copying of the SQLite file or backup; malicious or malformed data imports; replayed payment submissions; an untrusted renderer invoking Tauri commands; lost devices; and staff sharing credentials. Physical possession of an unencrypted Windows computer is a significant risk. The application cannot guarantee protection against a compromised operating system or an administrator with unrestricted machine access.

## 3. Roles
- **Owner/Admin:** Restaurant setup, staff and roles, all reports, backups/restores, tax and printer settings, sensitive adjustments.
- **Manager:** Operational oversight, reservations, table transfers, approved discounts, voids/refunds within configured limits, shift review; no unrestricted account/security administration.
- **Cashier:** Create/edit open orders, collect payments, issue standard invoices, open/close own shift, view permitted sales.
- **Kitchen:** View KOTs, update preparation status; no payment or financial settings access.

An installation may allow multiple roles per user; effective permissions are the union of assigned grants except where explicit separation-of-duties policy applies.

## 4. Permission matrix
| Action | Admin | Manager | Cashier | Kitchen |
|---|---|---|---|---|
| View dashboard | Yes | Yes | Limited | No |
| Create walk-in/table orders | Yes | Yes | Yes | No |
| Manage reservations | Yes | Yes | Configurable | No |
| Update KOT status | Yes | Yes | No | Yes |
| Collect payment | Yes | Yes | Yes | No |
| Apply ordinary discount | Yes | Within limit | Within limit | No |
| Void paid invoice/refund | Yes | Approval/limit | Request only | No |
| Modify menu/prices | Yes | Configurable | No | No |
| Close own shift | Yes | Yes | Yes | No |
| View all shifts/profit reports | Yes | Yes | No | No |
| Manage staff/permissions | Yes | No | No | No |
| Backup | Yes | Configurable | No | No |
| Restore database | Yes + reauthentication | No | No | No |
| Change tax/invoice settings | Yes | No | No | No |

Every permission is represented by a stable string such as `orders.create`, `payments.collect`, `refunds.approve`, `backups.restore`.

## 5. Local authentication
1. First launch creates an owner account via an offline setup wizard; never ship a default password or shared PIN.
2. Staff sign in with a unique username/staff identifier and password or optional staff PIN. Use **Argon2id** with a unique random salt and calibrated parameters; never store plaintext or reversible credentials.
3. PIN-only access is a convenience option and must be protected by rate limits, lockouts, and short session lifetimes. Require full password reauthentication for sensitive actions.
4. Session tokens/handles are generated by the trusted Rust layer, expire after configurable inactivity, and are revoked on logout, account deactivation, or permission change.
5. Lock the application when idle and after Windows session lock when feasible. Do not leave payment/restore dialogs usable after session expiry.
6. Account recovery must be an explicit local administrative procedure. Never implement a hidden master password or universal recovery PIN.

## 6. Authorization implementation
- Tauri command handlers resolve the authenticated session and check permission before performing any action.
- Business services enforce contextual rules: discount caps, shift ownership, invoice state, manager approval, and refund limits.
- An approval is a separate, logged authentication event by an authorized manager/admin; do not accept a frontend-provided `approved=true` flag.
- Prevent users from approving their own restricted action when separation of duties is enabled.
- Apply least-privilege Tauri capabilities: only necessary commands, file paths, and plugins. Disable arbitrary shell execution and broad filesystem access.
- Validate all command payloads server-side and use parameterized SQL.

## 7. Financial integrity
- Never edit or delete finalized invoices/payments in place. Use linked void, reversal, adjustment, or refund records with reasons and authorization.
- All money values are integer paise. Compute totals and change in the trusted backend.
- Use SQLite transactions for payment + invoice + order status changes.
- Enforce unique invoice numbering and idempotency keys for payment attempts.
- A reprinted receipt must be visibly marked as a copy; printing does not create a second payment.
- Log attempts to exceed permissions and unsuccessful approvals.

## 8. Audit trail
Audit records should include: event ID, UTC timestamp, actor ID, effective role, action, entity type/ID, before/after summary (redacted), reason, approving actor when relevant, workstation identifier, and success/failure. Record sign-ins, failed logins, discount overrides, refunds, voids, table transfers, menu price changes, settings changes, backups/restores, exports, and invoice reprints.

Store audit records append-only at the application layer and restrict modification; consider hash chaining for tamper evidence. **Local audit logs are not tamper-proof against a machine administrator.** Avoid logging passwords, PINs, full payment credentials, or unnecessary customer information.

## 9. Data-at-rest and backups
- Store live database in the per-user or machine application-data directory with restrictive filesystem permissions; do not store it under the install directory.
- SQLite does not encrypt its file by default. If encryption at rest is required, evaluate a supported encrypted SQLite solution and secure key handling; Windows BitLocker can additionally protect a lost device.
- Backups may contain all sensitive data. Offer encrypted backups with a user-held passphrase, integrity verification, and clear warnings about lost keys.
- Use SQLite's supported online backup mechanism, not a naive copy of an active WAL database.
- Validate backup format/version and integrity before restore. Create a safety backup, require admin reauthentication, and restore atomically with a rollback plan.
- Never overwrite a database silently on reinstall, update, or restore.

## 10. Privacy and payment information
Collect only information needed for operations. Customer name/phone on reservations should be optional unless restaurant policy requires it. Restrict access and provide retention/export/delete procedures consistent with accounting and legal obligations. Record cash/UPI/card **payment method and reference/status only**; do not store card PAN, CVV, UPI PIN, or bank credentials. Recording a UPI/card payment offline is not proof that an external payment succeeded; staff must verify it separately.

## 11. Local files, printing, and exports
- Restrict import/export dialogs to explicit user-selected paths; validate extensions, file signatures, schema, and sizes.
- Sanitize all receipt/KOT content and escape renderer output; treat menu and customer strings as untrusted.
- Print only to selected/configured Windows printers. Log reprints and failed jobs without duplicating charges.
- Warn before exporting reports to shared folders or removable drives.

## 12. Secure desktop lifecycle
Sign Windows installers when feasible; verify release provenance, dependencies, and hashes. Keep Tauri, Rust crates, and JavaScript dependencies updated through an offline-friendly signed installer process. Migration scripts must be versioned, transactional where possible, and tested against older databases. Disable development tools in production unless required for support, and avoid exposing a local network server by default.

## 13. Failure handling
- **Failed login:** generic error, bounded retry delay, audit entry.
- **Session expiry mid-order:** preserve safely committed order state; require sign-in before further privileged actions.
- **Unauthorized refund:** reject in Rust, keep original records intact, log attempt.
- **Database busy/full/corrupt:** stop unsafe writes, show actionable error, avoid partial financial records.
- **Restore failure:** retain original database and safety backup; provide clear recovery instructions.
- **Printer failure:** persist print job and payment independently; allow controlled retry.

## 14. Configuration decisions to finalize
1. Single Windows account or multiple Windows users on the same PC?
2. Mandatory passwords for all staff, or short PINs for cashier/kitchen roles?
3. Inactivity timeout (suggested starting point: 5–15 minutes for cashier terminals).
4. Cashier discount cap and manager refund approval threshold.
5. Whether manager can export backups and view customer contact details.
6. Required retention period for financial and audit data, subject to applicable law.
7. Whether full-disk/database/backup encryption is mandatory for deployment.

Until decided, use conservative defaults: admin-only restore, no cashier refunds, password for sensitive actions, least-privilege access, and no unencrypted automatic export to removable media.

## 15. Acceptance criteria
- A cashier cannot invoke an admin-only Tauri command even with a modified frontend.
- Disabled staff accounts cannot start new sessions; revoked sessions lose access.
- Five rapid wrong PIN attempts trigger configured throttling or lockout.
- Every paid invoice void/refund requires an authorized, recorded action.
- Repeated identical payment requests do not create duplicate payments.
- Backups are consistent and can be restored to a test installation.
- A failed restore leaves the previous database usable.
- Logs never contain plaintext passwords, PINs, CVV, or card numbers.
- Printer failure never removes a completed transaction.
- Staff can continue permitted operations without internet.

## 16. AI coding agent implementation rules
1. Build a centralized Rust authorization service; never duplicate security policy only in React.
2. Use typed command DTOs, explicit validation, and narrow Tauri permissions.
3. Add automated permission-matrix tests and adversarial command tests.
4. Keep security-critical operations auditable and transaction-safe.
5. Treat pending policy choices as configurable requirements; do not invent regulatory compliance claims.
6. Cross-reference `09-database-schema.md`, `10-business-rules.md`, `11-offline-data-management.md`, and `12-printing-and-billing.md`; reconcile conflicts before coding.

## 17. Definition of done
Security and permissions are complete only when authentication, authorization, approval workflows, audit logging, backup protection, financial integrity, and offline failure cases are implemented and verified in a packaged Windows build.
